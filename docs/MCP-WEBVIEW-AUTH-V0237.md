# ChatGPT MCP Tunnel v0.2.37 — WebView2 для входа, MCP для сообщений

## Архитектурное правило
WebView2 используется только для интерактивного входа на chatgpt.com и хранения постоянного профиля. Код **не** вызывает DOM, не вводит текст, не нажимает «Отправить», не извлекает переписку и не читает cookie/token. Все сообщения между локальным окном и моделью должны проходить через механизм MCP Apps и `ui/message`, а ответы — через `chat.reply`.

## Повторное использование проекта «Мост»
Исходный репозиторий: https://github.com/lvlaksim1/chatgpt-desktop-local-bridge
- `MainWindow.xaml.cs`: `CoreWebView2Environment.CreateAsync(userDataFolder: ...)` и постоянный профиль.
- `MainWindow.Tabs.cs`: `EnsureCoreWebView2Async`, `NavigationCompleted`, перехват окон авторизации в одном окружении.
- **Не переносить** `SendTextToChatAsync`, `Input.insertText`, `submitNativeSend`, `bridge-adapter.js` и наблюдателей DOM.

Для WinForms-агента используется `Microsoft.Web.WebView2.WinForms.WebView2`. Профиль: `%LOCALAPPDATA%\ChatGPTMCPAgent\WebView2\ChatGPT`. Он не удаляется при обычном обновлении.

## Протокол MCP
Официальные источники:
- https://github.com/openai/mcp-extensions/blob/main/docs/spec.md
- https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx

После фактического вызова `chat.ui.open(chat_id)` со стороны Host компонент MCP Apps начинает опрашивать очередь автоматически: нажимать «Начать передачу» не требуется.
- Существующий диалог: `ui/message` с `openai/message.target="active"`.
- Явно новый чат: `target="new"`.
- Видимый текст: только собственно пользовательское сообщение.
- Маршрут ответа `chat.reply(message_id=..., reply=...)` передаётся отдельным контентным блоком с `annotations.audience=["assistant"]`, без загромождения видимой истории.
- При недостоверном ACK не отправлять сообщение повторно без подтверждения; очередь и ID остаются на диске.

## Что подтверждено, а что нет
- Подтверждено локально: WebView2 Runtime на DOMKAT запускается, изолированный профиль создаётся; файл формируется и отображается окно входа. Программа не читает содержимое страниц и не использует браузерный транспорт для сообщений.
- Подтверждено локально в моделируемом хосте: MCP Apps автоматически запускает очередь при получении `chat_id`; содержание `ui/message` разделено на пользовательское и блок только для модели; маршрутизация, ACK, повтор после явного отказа и защита от дублей проходят тесты.
- **Не подтверждено реальным ChatGPT Host**: сквозной автоматический обмен и получение ответа `chat.reply`; применение `assistant`-адресации именно этим хостом; восстановление MCP Apps после закрытия хостом.
- **Нельзя приравнивать** WebView2-профиль к контексту ChatGPT Host: WebView2 логин не даёт приложению права создавать MCP iframe или получать ответы. Согласно спецификации, host создаёт iframe при вызове UI-инструмента и может завершить его жизненный цикл. Сервер MCP не может гарантировать автономное восстановление без участия хоста. Это остаётся отдельным критерием испытаний и исследовательским этапом.

## Удалённая реализация
В v0.2.36 экспериментально присутствовали `BrowserChatBridge.js` и Node/CDP для отправки сообщений через браузер. В v0.2.37 этот транспорт исключён из исходников и установочного пакета, его запуск отключён. MCP подключение и работа с компьютерами через Router Lite не меняются.

## Приёмка
1. Проверка входа и повторного открытия WebView2 с сохранённым профилем (без извлечения токенов).
2. Открытие MCP Apps в обычном ChatGPT и автоматический запуск без нажатия кнопки.
3. Два последовательных сообщения в уже привязанном локальном чате и два ответа по `chat.reply`.
4. Явно новый локальный чат создаёт новый обычный ChatGPT диалог; второй запрос идёт туда же.
5. После host teardown очередь сохраняется, повтор не создаёт дубликатов. Неподтверждённые пункты оставлять открытыми, не имитировать ответы через DOM.
