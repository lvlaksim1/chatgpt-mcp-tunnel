# Thread Relay / обновление MCP Tools — результаты реальных испытаний 30.10.2026

## Цель
Проверить, почему `chat.ui.open` отвечает `ok`, но не запускает автоматический опрос очереди, и перенести тестовый ретранслятор в подтверждённый Thread Entrypoint. Использован только MCP. Work/Codex/API и DOM-отправка исключены.

## Экспериментальная реализация
Ветка `experiment/thread-relay-host-20261030`. Редакции v0.2.39, v0.2.40, v0.2.41. Созданы `chat.thread.relay.probe` и ресурс `ui://chatgpt-mcp-tunnel/thread-relay-probe-v0240`. Новый iframe копирует протестированный `ChatRelayApp.html`, но **не имеет cross-chat discovery** и ограничен только явно выбранным canary chat_id. Логирует `ui-initialize`, `tool-input/result`, `relay-begin`, `relay-poll`, `ui-message` и heartbeat через `chat.lifecycle.event`. Пользовательская очередь не сканируется без привязки к canary chat_id.

Для вызова в существующей ChatGPT беседе новый tool `chat.thread.relay.probe` не был доступен в зафиксированной клиентской схеме (модель получила только старый инструментари й). Поэтому существующий `chat.thread.open` временно указывает на новый ресурс с canary chat_id из `%LOCALAPPDATA%\ChatGPTMCPAgent\Chat\thread-probe-chat-id.txt`. Если такого файла нет, chat_id пустой и очередь не обслуживается.

## Проверка версий
- v0.2.39 успешно собрана, установлена, MCP bridge_ping OK, Router Lite видит DOMKAT/MKATUSHONOK. Новый инструмент не появился в наборе доступных инструментов *текущей* беседы ChatGPT.
- v0.2.40 временно установлена. `chat.thread.open` вернул `resource=ui://chatgpt-mcp-tunnel/thread-relay-probe-v0240`, `chat_id=3b908f5ba39543e49b9a983c0f509308`. ChatGPT отобразил виджет, но события соответствовали прежнему `ChatLifecycleApp.html`: `ui-initialize`, `ui-initialized`, `tool-input`, `tool-result`, heartbeat с `instance=ui-...`. **Не было** `resource-read` с `source=thread-relay-probe`, `relay-begin` или `relay-poll`.
- v0.2.41 добавила в `chat.thread.open` отправку `notifications/tools/list_changed` через `McpServer.SendNotificationAsync`. Изолированный тест подтвердил фактическое получение JSON-RPC-уведомления MCP-клиентом. После установки и прямого вызова с ChatGPT Host: `tool-open` и `tool-call {source:tools-list-changed}` записаны, инструмент нового имени по-прежнему отсутствует в динамическом списке инструментов **этой** беседы, новая UI-программа не инициализирована.

## Основные выводы
1. `chat.ui.open` в v0.2.37 устанавливает локальный `ui-routes/status=ready` **до** появления iframe: ложная готовность. Это самостоятельная ошибка статуса, которую следует исправить независимо от транспорта.
2. Метаданные UI-инструмента/связанный HTML выглядят зафиксированными в контексте уже открытого ChatGPT диалога; изменение `_meta.ui.resourceUri` на сервере и успешный tool-result с новым URI не обязательно обновляют рендеринг. Вызов `notifications/tools/list_changed` в рамках этого экспериментального сеанса не привёл к видимому обновлению списка инструментов в модели или загрузке нового URI. **Это наблюдение именно данного Host-контекста, не универсальное отрицание поддержки уведомлений MCP.**
3. Изолированные .NET/MCP/Router Lite тесты и полные Inno-пакеты v0.2.39/40/41 прошли, но реальное ui/message из нового Thread relay не было отправлено: по безопасности сначала ожидали heartbeat `relay-poll`, который не появился. Успех E2E **не доказан**.
4. Новые соединения/чаты ChatGPT могут иначе переоткрывать tool metadata. Проверка в новой обычной беседе ещё не проводилась, не подменять её догадкой.
5. По спецификации MCP 2025-11-25 `notifications/tools/list_changed` допустимо; SDK отправляет его на транспорт. Host-реакция — отдельный критерий.

## Следующий технический эксперимент
- Разделить Host схему tools/list и версионированный HTML resource cache: изучить lifecycle подключения коннектора в одной беседе и новой обычной беседе, варианты ручного/программного обновления схемы без пользовательских действий.
- Использовать *существующий доступный* UI-инструмент и известный URI в новом обычном контексте для подтверждения автозапуска canary; не запускать локальную очередь, пока Host не зарегистрирует `relay-begin` и `relay-poll`.
- Исправить псевдо-статус ready: только событие фактически выполняемого MCP Apps делает соединение ready, model-invoked `chat.ui.open` означает opening.
- После реального старта отправить **одно** тестовое сообщение и проверить `ui-forwarded` и настоящий `chat.reply`, затем 10/10.

## Защита данных
В испытании не удалялись, не отправлялись и не модифицировались старые pending + ui-forwarded сообщения. Отдельный canary chat_id был пустым, живых `ui/message` не инициировали. Один VPN, один туннель, сервер DOMKAT. Полноценный чат по-прежнему НЕ ПРИНЯТ.

## Повторная приёмка 30.10.2026 — Refresh установленного MCP плагина и реальный E2E

### Снимок инструментов ChatGPT
- После установки runtime v0.2.41 новый инструмент chat.thread.relay.probe отсутствовал даже в новом обычном ChatGPT диалоге.
- В Settings -> Plugins -> ChatGPT MCP Tunnel -> Manage найдена и выполнена штатная кнопка «Обновить инструменты». Плагин в статусе DEVELOPMENT.
- После Refresh создан ЕЩЁ один новый обычный ChatGPT чат. Модель увидела и вызвала chat.thread.relay.probe с изолированным chat_id 3b908f5ba39543e49b9a983c0f509308.
- Host загрузил именно новый ресурс ui://chatgpt-mcp-tunnel/thread-relay-probe-v0240 (resource-read source=thread-relay-probe). Появились relay-bound, relay-poll, relay-pending и heartbeat source=relay-running. Автозапуск iframe и опроса очереди после штатного обновления регистрации доказан.
- Однократная GUI-операция создания диагностического нового ChatGPT чата НЕ является транспортом сообщений туннеля. Передача из локального приложения выполнялась через MCP ui/message.

### Первая настоящая автоматическая доставка прошла
- Canary message_id 0f62f2defcb04778a60437fc83157760, created 15:52:34 UTC; текст запроса: «MCP E2E проверка. Ответь ровно фразой: МАРШРУТ MCP РАБОТАЕТ.».
- Работающий MCP iframe увидел pending, выполнил ui/message target=active send=true. Файл ui-forwarded создан 15:52:36 UTC, transport=mcp_apps_ui_message.
- Модель вызвала chat.reply, запись получила Status=answered в 15:52:46 UTC и точный ответ «МАРШРУТ MCP РАБОТАЕТ.». Дубликата файла нет.
- Это подтверждение 1/1, но не приёмка 10/10.

### Повторный вызов: ACK есть, ответа нет
- Canary message_id 52382de5d39f4f6ea2178de0781b260f. Вторая запись была обнаружена, ui/message вызван, ui-forwarded создан в 15:55:29 UTC. Ответ через chat.reply отсутствует; Status=pending ещё в 15:59:45 UTC.
- Автоматический драйвер остановил 10/10 на втором сообщении, без отправки остальных и без повторов. Второе НЕ удалять и НЕ переотправлять: forwarded=true, результат генерации неопределённый.
- После второго запроса iframe продолжал heartbeat и relay-poll. Отсутствие ответа нельзя объяснять остановкой опроса. Фактическое появление второго текста в видимой беседе пока не подтвердилось.
- ACK от ui/message не означает запуска модели и не равно chat.reply.

### Служебная информация оказалась видимой
- Через Windows UI Automation прочитан текст первого user message в обычном ChatGPT: в нём присутствует служебная строка о маршруте chat.reply, message_id, хотя она передана как content block с annotations.audience=["assistant"].
- По реальному отображению текущая адресация не скрывает метаданные в ChatGPT. Официальная спецификация обещает скрытие assistant-only, но в нашем Host это не выполнено. Дефект обязателен к исправлению.
- Следующий эксперимент: использовать ui/update-model-context для model-only маршрута отдельно от чистого видимого ui/message. Поддержка capability заявлена Host, реальная доставка model context ещё не проверена.

### Инженерный вывод
- Проблема регистрации MCP-инструментов решена штатным Refresh на странице управления плагином. Ни переустановка сервера, ни notifications/tools/list_changed сами по себе не обновили снимок.
- Новый Thread Relay доказанно работает на первом автоматическом сообщении.
- Для продукта остаются две критические проблемы: повторные вызовы ui/message и скрытие маршрута от пользователя. Не объявлять чат готовым.
- Перед возвратом с временной v0.2.41 на стабильную v0.2.37 необходимо обновить инструменты плагина снова, чтобы снимок ChatGPT соответствовал установленному MCP серверу.
