# MCP Tunnel — аудит функциональности чата и критерии приёмки

Дата: 31.10.2026 (МСК). Объект: установленная v0.2.49 на DOMKAT, ветка feature/webview2-primary-ui-v0248, коммит d9caa65. Аудит выполнен по исходникам и доступным локальным данным, без изменений чатов, без отправки тестовых сообщений в облако.

## Цель
Полноценный самостоятельный клиент ChatGPT в окне MCP Tunnel. Функции стандартного ChatGPT Chat, доступные пользователю в браузере с тем же аккаунтом/планом, должны быть доступны в приложении, включая современную визуализацию, полноценные вложения, изображения, документы, состояние генерации, историю, переключение чатов и восстановление. Work/Codex и отдельный API не нужны. Приёмка до передачи пользователю, а не тестирование пользователем вместо разработчика.

## Подтверждённые исходным кодом блокирующие проблемы

### P0. Потеря нетекстового результата и несоответствие интерфейсу браузера
WebViewChatHost.SnapshotScript и WaitReplyAsync читают string Last посредством innerText. Answer сохраняет string Reply; ChatWindow использует RichTextBox и Append(string).
В текущей схеме отсутствует структура частей ответа с типами (текст, изображения, файлы, таблицы, формулы, ссылки, диаграммы, интерактивное содержимое), загрузка изображений и их рендеринг. Пользовательский реальный кейс: сгенерированный котёнок виден в WebView2, но полностью отсутствует в окне чата.
Вывод: смена одного CSS-селектора недостаточна. Нужно прекратить дублирующее извлечение и рендеринг ответа текстовой строкой.
Рекомендуемое решение: видимый WebView2 в центральной части главного окна чата (рендерить оригинальную страницу/контент ChatGPT), над которым приложение даёт собственную обвязку. Единый WebView2 — источник правды для отображения, отправки, вложений и статуса. Локальные ID и метаданные остаются только для управления из Tunnel, не подменяют облачную историю.

### P0. Зависание очереди при сбое вложения или неизвестном маршруте
WebViewChatHost.DeliverAsync вызывает AttachAsync до записи claim и до try/catch; при исключении выше catch событие в TickAsync логируется, но Pending остаётся. FindPending выбирает самый ранний pending по CreatedUtc, поэтому при повторном цикле выбирается проблемный элемент, а следующие сообщения не отправляются.
FileNode и DOM.setFileInputFiles не ожидают подтверждения загрузки: вместо проверки UI использован фиксированный Task.Delay(1800).
Для unbound chat Route возвращает null, а pending остаётся в очереди без видимого сообщения; это подтверждается двумя текущими pending после активации.
Решение: детерминированные состояния queued/uploading/uploaded/sending/sent/streaming/answered/failed/needs_reconciliation, на каждое сообщение отдельная ошибка, отсутствие head-of-line blocking; не создавать дубль при неизвестном статусе доставки.

### P0. Ненадёжное завершение генерации / ложный ответ
WaitReplyAsync считает ответ готовым только если Assistants>baseline, Last непустой и ~3 секунды стабилен; цикл длится около 3 минут. Нет достоверного отдельного состояния результата генерации изображений и файлов.
В SnapshotScript есть резервное чтение parentElement.innerText, возвращающее служебное ChatGPT сказал:ChatGPT как будто это ответ модели.
Нет явно поддерживаемой остановки генерации, возобновления после сетевой ошибки с точной сверкой полученного контента.
Решение: опираться на фактический UI ChatGPT и жизненный цикл его сообщений, не трактовать fallback текст заголовка как содержимое.

### P0. Восстановление после аварии
RecoverAsync обрабатывает только claim.state=sent, но не reserved. Claim.state=reserved создаётся до отправки, а переход в sent делается позже; при сбое возможны потеря/зависание.
При неизвестном состоянии не выполнять автоматическую повторную отправку, но предоставлять пользователю видимый статус и кнопку безопасной сверки/повторного действия.

### P1. Список и история чатов
ChatWindow.RefreshMessages берёт TakeLast(100) локальных записей. История облачного чата сканируется по DOM и сохраняется как тексты, не мультимедиа. Создание нового чата не запрашивает название; нет локального удаления через ПКМ; список нельзя растягивать. Переключение двух чатов и импорт длинной истории требуют синхронизации с облачной реальностью.
Удаление локальной привязки и удаление из ChatGPT должны быть двумя разными явно названными операциями. Не удалять облачные беседы автоматически.

### P1. Полноценный ввод и результат
Нет редактирования отправленного сообщения, регенерации ответа, обычного browser copy / code copy, корректной подсветки кода, интерактивных ссылок/источников, работы с таблицами и математикой, открытия изображений/файлов и предпросмотра, а также модели/режима управления ChatGPT по возможностям аккаунта. Не проверены drag/drop, paste image, несколько вложений, большие файлы, отмена загрузки.
При полном WebView2 отображении и нативной странице ChatGPT большинство этих функций доступны без копирования реализации каждого компонента. Особые элементы MCP Tunnel должны оставаться совместимыми с ними.

### P1. UX и темы
Требуются modern chat layout, немедленное отображение первого сообщения, интерактивный разделитель, именование/удаление чатов, индикаторы загрузки, прокрутка без принудительного возврата вниз при чтении истории, плавный streaming, отсутствие вспомогательных DOM текстов, сохранение акцентных цветов в обеих темах. Темы главного окна, настроек, заголовков, полосы прокрутки и передачи файлов должны переключаться мгновенно.

### P1. Доступ к системе
Отдельная привилегированная служба после однократного UAC, защищённый локальный транспорт, проверки аутентичности клиента, постоянное право модели на разрешённые админ-операции. Не путать админ-доступ с разрешением на любую неограниченную команду от другого процесса.

## Архитектурный принцип следующей версии
1. Один WebView2-профиль, один активный web ChatGPT session и один источник состояния отправки/ответа.
2. Рендеринг всех результатов оригинальным движком страницы ChatGPT в *основном окне*. Отказ от text-only RichTextBox как основного рендера. Внешняя WinForms/собственная оболочка может управлять чатами и инструментами, но не дублировать богатый web UI без нужды.
3. Локальная очередь нужна для модельных/автоматизированных команд и IPC; ручной ввод в web composer не должен дублироваться локальной очередью.
4. Модельные операции и системные инструменты должны продолжать работать без Work/Codex и отдельного OpenAI API. Модельная сессия ChatGPT соответствует обычному Chat.
5. Ошибка одного сообщения не блокирует очереди других чатов. Ошибка загрузки одного файла не блокирует следующий обычный текст.

## Обязательные E2E-приёмки до выпуска
A01 новый чат и первое сообщение видно немедленно;
A02 два и 10 последовательных сообщений в одной облачной беседе, контекст сохраняется;
A03 переключение между 2-3 чатами и возврат, точные облачные URL;
A04 перезапуск приложения между сообщениями, сохраняется ответ/контекст;
A05 отключение/восстановление Happ и WebView2; нет потерь, дублирования и вечной очереди;
A06 отправка одного и нескольких TXT/DOCX/PDF/XLSX/PNG/JPG, подтверждение что модель действительно прочитала содержимое;
A07 ошибка вложения, затем обычное текстовое сообщение доставляется;
A08 генерация изображения, показ изображения внутри основного окна, открытие/сохранение;
A09 ответ с прикреплённым файлом, показ и сохранение;
A10 генерация ответов Markdown: заголовки, списки, таблицы, код, математика, ссылки и цитирования;
A11 streaming без служебного ChatGPT сказал:ChatGPT, нормальное завершение и stop;
A12 Edit / Regenerate / Copy (если доступны в исходном ChatGPT);
A13 импорт существующего длинного облачного чата с полным историческим содержимым;
A14 новая сессия с пользовательским названием, rename, контекстное delete, перетаскиваемая граница;
A15 тест многотысячной истории сообщений без потери/зависания и без насильственного автоскролла;
A16 paste images, drag/drop, запуск из трея, закрытие и восстановление;
A17 смена темы всех окон и цветов при генерации/уведомлении;
A18 установка поверх работающего приложения, автоматическое закрытие, rollback;
A19 MCP ping, инструменты DOMKAT и MKATUSHONOK, UAC-служба после перезагрузки;
A20 тестировка обычного Chat, без переключения на Work/Codex;
A21 отсутствие ошибок JavaScript, переполнения хранилища и незащищённой утечки профиля/токенов;
A22 повторная проверка на настоящем аккаунте через браузерный ChatGPT после каждого существенного изменения его DOM.

## Критерии выпуска
Нельзя объявлять готовность по build + unit-tests. Каждый пункт A01-A22 должен иметь автопротокол PASS/FAIL с датой, версией, типом окружения и проверяемым фактическим результатом. Блокирующие P0 должны быть устранены, остальные ограничения явно отмечены. Не использовать пользовательские рабочие чаты для разрушительных тестов. Отдельная успешная авторизация не равна успешной отправке. Никаких «готово» до реального E2E.
